## Implementation note: the seat counter and the 1000-expression limit (R54, 2026-10-08)

`bookedCount` and the per-tier counters may now ONLY move through a path that ties the change to a
specific booking: `capacityBump`, `capacityRelease`, `capacityReleasePartial` and `tierReleaseOk`.
The plain event-edit branch (`eventEditOk`) pins both. Before this, anyone with `canRunBookings()` —
`venue_host` included — could lower `bookedCount` or reset a tier counter by hand and so release
seats without passing the `canRefund()` gate, which defeated R54.

**Ordering is load-bearing, not style.** Firestore rules evaluate at most 1000 expressions per
request. `eventEditOk` must test the `bookedCount` pin FIRST, before `validBookingEvent` (10
`tiersOk` calls and more), and `capacityRelease`/`capacityReleasePartial` must do their cheap shape
checks before the role lookup. Putting the pin after `validBookingEvent` burns the budget on the
branch that is about to fail, leaving too little for the release branches that follow, and
legitimate host cancels start failing with
`Unable to evaluate the expression as the maximum of 1000 expressions to evaluate has been reached`
— an error that points at the write, not at the cause. It only shows for non-super-admin callers,
because `hasRole()` costs several expressions per call while a super admin needs one `exists()`.
The `counters cannot be unwound by hand (R54 bypass)` tests in `tests/rules/bookings.rules.test.ts`
are the safety net; run them after ANY change to these functions.

**A4 (2026-10-09): 10-tier events.** Measured by padding a rule with `true && ...` chains until it hit the
limit (1 pad unit ~ 3 expressions): a role-based `host` editing ONE field of an event with 5 full tiers
(capacity + seatsPerTicket) already failed; even 0 tiers used ~720 of 1000. After the restructure the same
host edit of a 10-tier event uses ~370 (super admin ~340), independent of tier count. Changes:
`isHost()`/`canRunBookings()` do ONE users/{uid} read via `hasAnyRole` (same answer as OR-ing `hasRole`);
`validBookingEvent(eventId, ch, oldTiers)` validates a field only when the write sets/changes it (`ch` =
affected keys on update, all keys on create) and skips each group with one `hasAny`; tiers are validated
by `tierOk(t)` (one call per tier, the map evaluated once as the argument: unrolling inline was MEASURED
more expensive, ~119 vs ~76 per tier, because every `l[i]` re-indexes), dispatched on the list size once
(`tiersNew`/`tiersChanged`), and on update only new or changed tiers pay. The cutoff check compares before
calling `isAdmin()`. KNOWN GAP: a write that must validate ALL 10 tiers at once (a fresh 10-tier create, or
an update that changes every tier) by a role-based host still exceeds the budget (each full tier costs ~60;
a create needs ~470 before tiers). The regression test for that case is `it.skip` with a note; the next
lever is cheaper per-tier checks (each primitive check costs ~6, a 10-element `in` list ~15).

Also fixed in the same pass: `capacityRelease` accepted only `reserved`/`paid_mock`, so releasing a
`checked_in` booking of a cancelled event (which `cancelShape` allows) was silently riding on the
plain edit branch. It now mirrors `cancelShape`.
